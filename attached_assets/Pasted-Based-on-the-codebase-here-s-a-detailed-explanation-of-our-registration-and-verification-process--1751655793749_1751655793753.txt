Based on the codebase, here's a detailed explanation of our registration and verification process:
Registration Flow Overview
The system implements a multi-stage registration process with email verification, passport claiming, and admin approval. Users progress through different states based on their completion of various verification steps.
User States and Transitions
1. user_logged
Condition: User logs in with Farcaster but hasn't approved their signer(app)
Derived: waiting_app_approval
Action: User must approve their Farcaster signer via QR code
2. pending_id_verification (old signer_approved)
Condition: Signer approved, but no email or passport verification
Derived: signer_approved
Action: User redirected to ID verification page
Next: email verification AND passport claiming (any order but both required)
3. pending_id_verification (email_verified=true)
Condition:
User enters email address
System sends 6-digit verification code (10-minute expiry)
User enters code to verify
Update email_verified status to true.
Derived state: 
Next: if passport validated or approved, redirect to Home page with final permissions. If not, stay on app_approved state.
4. pending_id_verification (passport_verified=true)
Path A: Existing Domain Verification
Condition: User owns existing *.ipecity.eth domain
Process:
User connects wallet
System detects existing ENS domain via JustaName API
User signs message to prove ownership
Result: Immediate active member status (if email already verified)
State: active_member
Path B: New Username Claiming
Condition: User doesn't own an existing domain(passport)
Process:
User connects wallet and system don’t detect existing ENS domain.
User starts an application process by clicking in “start application process”
App opens Profile page (should have username there)
User enters desired username (system pre fill out with farcaster username).
System checks availability via JustaName API
User submits the application process after fill out all required info 
Status becomes pending_claim -> pending_application
Next: Admin approval required
5. Pending Claim State Pending Application State
Condition: User claimed a new username but the admin hasn't approved
Admin Action: Admin reviews application process and either:
Approves/architect: Creates JustaName invitation and sets user as architect (member type).
State: approved_architect_application
Process: the user must accept invitation (sign the wallet)
Approves/explorer: sets user as explorer (member type)
State: approved_explorer_application
Process: the user has now access to explorer-only pages
Denies: Updates to denied status
State: denied_application
Process: the user is shown a message to try again in a few months.
6. Invitation Acceptance Approved Architect Application
State:approved_architect_application member (after admin approval)
Process:
User sees "Verify Passport" button
Clicks button to accept JustaName invitation
Uses JustaName SDK acceptSubname hook
Subdomain becomes active on blockchain
State: active_member
Result: Full verification complete. Access to the member pages if email verified.
7. Invitation Acceptance Approved Explorer Application
State:approved_explorer_application member (after admin approval)
Process:
User sees result of the application and can have access to the explorer-allowed pages.
Result: Full verification complete. Access to the member pages if email verified.
7.  Invitation Acceptance Denied Application
State:denied-application (after admin denial)
Process:
User sees the message “Your application has not been approved”.
Result: Full verification complete. Access to the explorer-only pages.
