### Why the signature bombs out

`ethers.verifyMessage()` (and the `siwe` helper that calls it under the hood) expects a **65-byte** secp256k1 signature that looks like

```
0x47…e7a7b0c1e1d8f79f12b29e0bbf2c6310c81743cc2f1b7484e31bdb0b012f7251b
```

What you’re passing back from the client is **hundreds of bytes long**.
That happens when the wallet signs something that **isn’t a plain string**:

* `wagmi` sees an **object** and falls back to `signTypedData`, or
* a smart / pass-key wallet (e.g. Coinbase Smart Wallet) wraps the sig in an ERC-6492 envelope.

Either way, the server tries to treat that monster as a raw 65-byte sig and throws **`invalid raw signature length`**.

---

### Two quick fixes

|                                                                                  | What to change                                                                                                                           | Why                                                                     |
| -------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| **1. Sign the real SIWE string**                                                 | Turn the `SiweMessage` object into the canonical string before calling `signMessage`.                                                    | Ensures the wallet produces a normal 65-byte `personal_sign` signature. |
| **2. Verify with the same SIWE helper that understands smart-wallet signatures** | Use the v3 `siwe` verify helper or viem’s `verifySiweMessage`, which know how to fall back to ERC-1271/6492 when the sig isn’t 65 bytes. | Lets EOA and smart-wallet users sign in the same flow.                  |

Below are the minimal **line-level edits** needed on both sides.
(Everything else can stay as-is.)

## 2 ▪ Backend (`/api/passport/verify` route)

```ts
import { SiweMessage } from "siwe";
import { verifySiweMessage } from "viem/siwe";   // viem ≥ 2.10 (handles ERC-1271/6492)

export async function verify(req, res) {
  const { message, signature, walletAddress, nonce, domain } = req.body;

  // Re-create the message
  const siwe = new SiweMessage(message);

  try {
    // viem helper => understands EOAs *and* smart-wallet sigs
    const { success } = await verifySiweMessage({
      message,
      signature,
      domain: process.env.EXPECTED_DOMAIN,
      nonce: storedNonceForSession,
      // transport: http(), // pass an RPC transport if you need 1271 checks
    });

    if (!success) throw new Error("Signature does not match message");

    // ✅ everything checks out
    …
  } catch (err) {
    return res.status(400).json({ error: `Signature verification failed: ${err.message}` });
  }
}
```

### A couple of extra safety notes

1. **Nonce & Domain**:
   Generate the nonce server-side, store it in the user’s session, and send it down to the client. Never create it in the browser like `Math.random()` or you lose replay-attack protection.

2. **Smart-wallet users**:
   If you want to support Coinbase Smart Wallet / ERC-4337 accounts, keep the `verifySiweMessage` flow (or call `isValidSignature` yourself). Otherwise reject anything that isn’t 65 bytes to keep the logic simple.

3. **Same address**:
   Confirm that the `walletAddress` you send is the one the wallet is currently connected with (`useAccount().address`). A mismatch here throws the same “signature does not match address” error.

Apply the snippets above and your SIWE login should work for a plain EOA—and won’t blow up when a smart wallet shows up either.
