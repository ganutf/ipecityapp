Below is the playbook most Farcaster apps follow to stay logged-in after a page refresh.
It works whether you use plain React/Vite or Next.js/Next-Auth; the only difference is where the “session blob” is stored (browser storage vs. an HttpOnly cookie).

1 Capture the credentials once, right after the user signs in
tsx
Copy
Edit
import { useEffect } from "react";
import { useProfile, useSignInMessage } from "@farcaster/auth-kit";

export function PersistLogin() {
  const { isAuthenticated, profile } = useProfile();
  const { message, signature } = useSignInMessage();     // <-— the SIWF payload

  useEffect(() => {
    if (isAuthenticated) {
      localStorage.setItem(
        "fcAuth",
        JSON.stringify({ message, signature, fid: profile?.fid })
      );
    }
  }, [isAuthenticated, message, signature, profile]);
}
Why?
AuthKit stops at “user is authenticated in memory”. After a hard refresh React remounts and AuthKit’s internal state is empty. By caching the SIWF message + signature (or, if you are also adding a signer, fid + signer_uuid), you have everything needed to recreate the session. 2 On first paint, check whether a cached session exists
tsx
Copy
Edit
import { AppClient } from "@farcaster/auth-kit/client";

const appClient = new AppClient({ relay: "https://relay.farcaster.xyz" });

export async function restoreSession(setAuthState: (fid:number)=>void) {
  const cached = JSON.parse(localStorage.getItem("fcAuth") || "null");
  if (!cached) return;

  const { message, signature, fid } = cached;

  // ⚡  Lightweight server-side verification (best practice)
  const { success } = await appClient.verifySignInMessage({
    domain : window.location.host,
    nonce  : JSON.parse(message).nonce,  // same nonce you used originally
    message,
    signature,
    acceptAuthAddress: true
  });                                                  :contentReference[oaicite:1]{index=1}

  if (success) setAuthState(fid);          // flip your own “logged-in” flag
  else         localStorage.removeItem("fcAuth");
}
You can do the verification in the browser (shown above) or on an API route and return a signed JWT / Next-Auth session; the flow is identical.
