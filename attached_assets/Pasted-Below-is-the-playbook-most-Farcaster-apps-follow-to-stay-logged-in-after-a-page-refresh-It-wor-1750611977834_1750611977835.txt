Below is the playbook most Farcaster apps follow to **stay logged-in after a page refresh**.
It works whether you use plain React/Vite or Next.js/Next-Auth; the only difference is where the “session blob” is stored (browser storage vs. an HttpOnly cookie).

---

## 1 Capture the credentials once, right after the user signs in

```tsx
import { useEffect } from "react";
import { useProfile, useSignInMessage } from "@farcaster/auth-kit";

export function PersistLogin() {
  const { isAuthenticated, profile } = useProfile();
  const { message, signature } = useSignInMessage();     // <-— the SIWF payload

  useEffect(() => {
    if (isAuthenticated) {
      localStorage.setItem(
        "fcAuth",
        JSON.stringify({ message, signature, fid: profile?.fid })
      );
    }
  }, [isAuthenticated, message, signature, profile]);
}
```

*Why?*
AuthKit stops at “user is authenticated *in memory*”.  After a hard refresh React remounts and AuthKit’s internal state is empty.  By caching the **SIWF message + signature** (or, if you are also adding a signer, `fid + signer_uuid`), you have everything needed to recreate the session.  Neynar’s own guide explicitly recommends persisting `signer_uuid` the same way ([docs.dynamic.xyz][1]).

---

## 2 On first paint, check whether a cached session exists

```tsx
import { AppClient } from "@farcaster/auth-kit/client";

const appClient = new AppClient({ relay: "https://relay.farcaster.xyz" });

export async function restoreSession(setAuthState: (fid:number)=>void) {
  const cached = JSON.parse(localStorage.getItem("fcAuth") || "null");
  if (!cached) return;

  const { message, signature, fid } = cached;

  // ⚡  Lightweight server-side verification (best practice)
  const { success } = await appClient.verifySignInMessage({
    domain : window.location.host,
    nonce  : JSON.parse(message).nonce,  // same nonce you used originally
    message,
    signature,
    acceptAuthAddress: true
  });                                                  :contentReference[oaicite:1]{index=1}

  if (success) setAuthState(fid);          // flip your own “logged-in” flag
  else         localStorage.removeItem("fcAuth");
}
```

*You can do the verification in the browser* (shown above) **or on an API route** and return a signed JWT / Next-Auth session; the flow is identical.

## 3 Next.js / Next-Auth variant (server-side cookie)

If you prefer an HttpOnly cookie instead of `localStorage`, drop the **Credentials provider** shown below into `app/api/auth/[...nextauth]/route.ts` and rely on Next-Auth to keep the cookie updated:

```ts
import NextAuth from "next-auth";
import Credentials from "next-auth/providers/credentials";
import { AppClient } from "@farcaster/auth-kit/client";

const appClient = new AppClient({ relay: "https://relay.farcaster.xyz" });

export const authOptions = {
  providers: [
    Credentials({
      name: "Farcaster",
      credentials: {
        message  : { label: "Message",   type: "text" },
        signature: { label: "Signature", type: "text" },
        nonce    : { label: "Nonce",     type: "text" }
      },
      async authorize(creds) {
        const { success, fid } = await appClient.verifySignInMessage({
          message : creds.message,
          signature: creds.signature as `0x${string}`,
          domain  : process.env.NEXTAUTH_URL,
          nonce   : creds.nonce,
          acceptAuthAddress: true
        });

        return success ? { id: String(fid) } : null;
      }
    })
  ],
  session: { strategy: "jwt", maxAge: 30 * 24 * 60 * 60 }   // 30 days
};

const handler = NextAuth(authOptions);
export { handler as GET, handler as POST };
```

*How this fixes refresh-logout*

1. Front-end calls `signIn("credentials", { message, signature, nonce })`.
2. `authorize` verifies the SIWF payload (just like the client snippet).
3. On success Next-Auth drops a secure, HttpOnly cookie.
4. Every new request (including the first SSR pass) rehydrates the session automatically, so `useSession()` is already valid when the page loads.

The complete demo lives in the AuthKit repo under **`examples/with-next-auth`** ([docs.farcaster.xyz][2]).

## 4 Adding **write** capabilities (signer\_uuid)

If your app lets users *like / recast* you also need to persist the signer:

```ts
// after signer creation
localStorage.setItem("fcSigner", JSON.stringify({ fid, signer_uuid }));
```

When the page reloads:

```ts
const saved = JSON.parse(localStorage.getItem("fcSigner")||"null");
if (saved) neynarClient.setSignerUuid(saved.signer_uuid);
```

Persisting `signer_uuid` is exactly what Neynar’s docs suggest ([docs.dynamic.xyz][1]).

## 5 Security & UX tips

| Topic                    | Recommendation                                                                                                                                       |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| Storage layer            | Use **HttpOnly cookies** (Next-Auth, `iron-session`, etc.) in production; reserve `localStorage` for quick prototypes.                               |
| Expiration               | Piggy-back on the SIWF `expirationTime` or signer’s `deadline` so the session transparently forces a re-login when the key is no longer valid.       |
| CSRF protection          | Next-Auth & Iron-Session include CSRF tokens by default; if rolling your own cookie, add a double-submit token.                                      |
| Multiple devices         | Persist the same `signer_uuid` server-side and return it to all logged-in clients so the user doesn’t pay to add a new signer for every browser tab. |
| Opt-in “remember me” box | Gate the persistence logic behind a checkbox if you need shorter-lived sessions on shared machines.                                                  |

---

### TL;DR

1. **Save** the SIWF `message` + `signature` (and optional `signer_uuid`) after the first login.
2. **Verify & restore** them on every page load (client-side or server-side).
3. For production apps, wrap the whole thing in Next-Auth (or any session middleware) and let it drop an HttpOnly cookie—problem solved.
